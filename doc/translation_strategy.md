# 일본어 스크립트의 한국어 번역 지침

## 목적과 적용 범위

이 문서는 이 저장소에서 `*_jpn.json`을 기반으로 같은 이름의
`*_kor.json`을 만들거나 수정할 때 적용한다. 번역문은 원본 바이너리의
동일한 주소 범위에 다시 기록되므로, 자연스러운 번역뿐 아니라 주소와
바이트 길이를 정확히 보존해야 한다.

참고 우선순위는 다음과 같다.

1. 같은 워크스페이스의 기존 `*_jpn.json`/`*_kor.json` 번역 쌍
2. 같은 파일과 인접 주소의 문맥
3. `custom_char.json`과 병합된 custom word 집합
4. 저장소의 `name_db/` 및 게임별 용어 자료

같은 일본어 문장이 기존 번역 쌍에 있으면 먼저 그 번역을 재사용한다.
다만 화자, 조사, UI 길이 등 문맥이 다른 경우에는 문맥에 맞게 조정한다.

## 반드시 지켜야 할 불변 조건

1. `START=END` 형식의 주소 시작점, 항목 순서, 주소 키 순서는 원본 순서를
   유지한다.
2. 주소와 값은 원칙적으로 `*_kor.json`만 수정한다. 끝 주소 확장이
   필요할 때만 원본 바이너리에서 다음 항목까지의 구간이 실제 `00`인지
   확인한 뒤 `*_jpn.json`과 `*_kor.json`에 같은 확장 주소를 적용한다.
   이때 `*_jpn.json`의 기존 원문 값은 유지하고, 추가된 구간만 null
   바이트 표기로 채운다.
3. 주소 확장 여부와 관계없이 `*_jpn.json`과 `*_kor.json`의 `=` 포함 주소
   키 집합은 완전히 같아야 한다.
4. 각 한국어 값의 인코딩 바이트 길이는 반드시
   `int(END, 16) - int(START, 16) + 1`과 같아야 한다.
5. 문자열 안의 서식 인자, 제어 코드, 포인터 및 원시 바이트를 일반
   문장으로 오인해 번역하지 않는다.
6. 일반 문자는 한국어 폰트 테이블에 있어야 하며, `{키}` 표기는 병합된
   custom word 집합에 있어야 한다.
7. JSON은 UTF-8, 유효한 객체 형식으로 저장한다. 파일명은 원본의
   `_jpn.json`만 `_kor.json`으로 바꾼다.

`write_script_auto.py`의 일반 문자열 기록 부분은 주소의 끝을 기준으로
자동 차단하지 않는다. 길이가 초과되면 다음 데이터까지 덮어쓸 수
있으므로 기록기를 실행하기 전에 별도로 길이를 검증해야 한다.

## 표기와 바이트 계산

| 표기 | 의미 | 길이 |
| --- | --- | ---: |
| 일반 문자 `가`, `_`, `.` 등 | 한국어 폰트 테이블의 2바이트 문자 | 문자당 2바이트 |
| `|X` | `X` 한 글자를 1바이트 테이블로 기록 | 1바이트 |
| `|_` | 1바이트 공백 | 1바이트 |
| `_` | 2바이트 공백 또는 길이 맞춤용 문자 | 2바이트 |
| `@` | 원래 바이너리 2바이트를 덮어쓰지 않고 건너뜀 | 2바이트 |
| `{키}` | 병합된 custom word 집합의 바이트열 사용 | 해당 16진수 문자열 길이의 절반 |
| `0x:16진수#설명` | 문자 변환 없이 원시 바이트 기록 | 16진수 문자열 길이의 절반 |

`|`는 독립된 문자가 아니라 바로 다음 한 글자만 1바이트로 만드는 접두
표기다. ASCII 서식 문자열은 각 글자 앞에 `|`를 붙인다.

- `%s` → `|%|s`
- `%d` → `|%|d`
- `%4d` → `|%|4|d`
- `DUMMY` → `|D|U|M|M|Y`
- `ＢＩＬ` → `|B|I|L`
- `４０％` → `|4|0|%`

짧은 주소 범위에서 숫자나 영문 약어가 들어갈 때는 전각 숫자·전각 영문보다
반각 ASCII 표기를 우선 검토한다. 단, `|`는 실제 1바이트 ASCII 또는 제어
문자 앞에만 붙인다. 한글 음절 앞에 `|`를 붙여 `|브`, `|이`, `|로`처럼
쓰면 존재하지 않는 1바이트 코드로 오해되므로 사용하지 않는다.

일반 문장 안에 실제 ASCII 공백을 직접 넣지 않는다. 한국어 어절 사이는
기존 번역본처럼 주로 `|_`를 사용하고, 2바이트 여백이 필요할 때만 `_`를
사용한다.

숫자, 금액, 수량, 서식 변수(`|%|d`, `|%|u`, `|%|l|u`, `|%|w` 등)가
한국어 어절 뒤에 바로 이어질 때는 가독성을 위해 앞에 `|_` 공백을 두는
것을 우선한다. 예: `20일마다|_|%|l|u`, `돈은|_|%|l|u|_크레딧뿐이다`.
단, 슬롯이 부족할 때만 이 공백을 줄이고, 문장 의미와 조사 연결이 깨지지
않는지 확인한다. 변수나 앞 조각에 붙는 조사가 불확정이면
`을|(를|)`, `은|(는|)`처럼 표시해 앞말 받침에 대응할 수 있다. 이때
괄호와 조사 표기도 실제 바이트 길이에 포함해 계산한다.

화면에 표시되는 마침표·쉼표·물음표·느낌표는 `|.`, `|,`, `|?`, `|!`
같은 1바이트 표기가 아니라 `.`, `,`, `?`, `!`의 2바이트 글자를 우선으로
기록한다. 공간이 부족할 때만 반각 문장부호를 사용하고, 같은 범위 내
문장부호 폭은 통일한다. 2바이트 쉼표나 마침표 뒤에는 글자 폭에 공백이
포함되므로 바로 뒤에 `|_`를 붙이지 않는다. 반각 쉼표나 마침표 뒤에
문장이 이어질 때만 필요에 따라 `|_`를 붙인다.
호칭이나 감탄사 뒤의 원문 쉼표가 문장 의미와 말투를 살리는 경우에는
어절 공백을 줄이거나 문장 끝 마침표를 `|.`로 줄여서라도 쉼표를 보존할
수 있다. 예를 들어 `若、指名手配者のシャトルですぞ。`는 공간이 부족하면
`|*도련님,지명수배자의|_셔틀입니다|.`처럼 호칭 쉼표를 살리고 끝 마침표를
반각으로 처리한다.

`custom_char.json`을 기준으로 PC-98 예제에서 확인되는 주요 표기는
다음과 같다.

| 표기 | 기록 바이트 | 용도 |
| --- | ---: | --- |
| `|␀` / `␀` | `00` / `0000` | 1바이트 또는 2바이트 널·여백 |
| `|␁` | `01` | 게임 제어 코드 |
| `|␂` | `0A` | 대사 줄바꿈 |
| `|␊` | `1B` | 게임 제어 코드 |

남는 공간을 널로 채울 때는 가능한 한 2바이트 단위의 `␀`를 우선 사용한다.
`|␀`는 홀수 바이트를 맞춰야 하거나 원문이 1바이트 널을 요구하는 경우에만
사용한다. 예를 들어 문장 뒤 4바이트가 남으면 `|␀|␀|␀|␀`보다 `␀␀`가
더 깔끔하다.

파일명, `printf` 형식 문자열 등 모든 글자가 `|X`로 구성된 기능성 ASCII
문자열은 원래 바이트 배열을 보존한다. `%s`, `%d` 등의 서식 인자와
`|␁`, `|␊` 같은 기능성 제어 코드는 의미를 확인하지 않고 삭제하거나
다른 문자로 바꾸지 않는다. 남는 공간을 채울 때도 종료 코드가 필요한
위치의 널을 단순 공백으로 교체하지 않는다.

`|␊|C|0|␊|B|7|___`처럼 문장 앞에 붙은 화면 제어 접두부는 그대로
보존하고, 실제 표시 문장에 해당하는 부분만 번역한다.

예를 들어 `"가|_나|␀"`의 길이는 `2 + 1 + 2 + 1 = 6`바이트다.
`0x:` 값에서는 `#` 앞의 짝수 길이 16진수만 실제로 기록되며, 기록 바이트
길이가 주소 길이와 정확히 같아야 한다. `#` 뒤 설명만 한글로 정리할 수
있고, 바이트 값은 명확한 패치 근거가 없으면 변경하지 않는다.

## custom word 사용

번역문이 주소 범위에 들어가지 않거나 고정된 용어·이름을 압축 코드로
써야 할 때 `{키}`를 사용한다. 한국어 번역에서 `{키}`는
`custom_word.json`, `custom_word_kor.json`, `custom_word_ext_kor.json`을
병합한 집합에 실제로 존재해야 한다.

```json
{
    "00919=00920": "{다이묘}정보"
}
```

- 키에 `|`나 `_`가 포함되어 있어도 키 문자열 전체를 그대로 사용한다.
- 임의의 `{새키}`를 만들지 않는다. 새 키가 필요하면 충돌하지 않는
  바이트 코드와 폰트 구성을 별도로 검토한 뒤 해당 custom word 파일을 함께
  수정해야 한다.
- `{키}`의 화면상 글자 수가 아니라 매핑된 16진수의 바이트 수로 길이를
  계산한다.
- 조사(`은`, `는`, `이`, `가`, `을`, `를`, `와`, `과`, `에`, `의`)의
  2바이트 압축 코드는 조사 뒤의 반각 공백까지 포함한다. 따라서
  `는|_`는 `{는}`으로 바꿀 수 있으며, `는|_|_`처럼 공백을 다시
  덧붙이지 않는다.

## 번역과 문체 원칙

1. 직역보다 게임 화면에서 자연스럽고 짧은 한국어를 우선한다.
   원문이 `A および B`처럼 병렬 구조여도 한국어에서 어색하면 의미 관계에
   맞게 재구성한다. 앞 동작이 뒤 목적을 위한 수단이면 `A와 B를 한다`보다
   `A로 B한다`처럼 옮긴다. 예: `障害物からの回避運動および当エリアからの
   脱出を試みます` → `장애물을|_피하는|_기동으로|_이|_구역에서|_탈출을|_시도합니다.`
   고정 byte에 맞추는 과정에서 한국어가 어색해지지 않도록, 먼저 자연스러운
   한국어 후보를 만든 뒤 byte를 계산한다. 길면 의미 손실이 적은 부사,
   중복 표현, 완곡 표현부터 줄이고, 짧으면 문장을 억지로 늘리기보다
   기존 관례의 공백·널 표기로 채운다. 예를 들어 `道中は物騒だから気をつけてな`
   는 byte에 맞는 `도중이|_위험하니|_조심하십시오.`보다 한국어 감각이 나은
   `길이|_위험하니|_조심하십시오.␀`처럼 조정한다.
2. 화자의 신분과 기존 말투를 유지한다. 같은 인물의 존대, 하오체,
   명령조가 대사마다 흔들리지 않게 한다.
   단일 문장만 보고 존대·반말을 정하지 말고, 같은 블록의 앞뒤 문장과
   화자 말투를 함께 확인한다. 인접 문장이 `じゃねえ`, `出ていけよ`,
   `くれや`처럼 거친 반말이면 `いらっしゃい` 같은 짧은 인사도
   `어서|_와라`처럼 같은 톤으로 맞춘다.
3. 일반 보고, 질문, 안내 문장에는 반말을 사용하지 않는다. 반말은 전투
   중 상대편에게 직접 하는 대사임이 명확한 경우에만 허용한다.
4. 인명, 지명, 관직, 아이템명, UI 명칭, 반복 문구는 기존 번역 쌍과
   데이터베이스의 표기를 우선해 통일한다.
   압축 가능한 인명·지명은 표기 통일과 길이 절감을 함께 고려해 병합된
   custom word 집합의 조합을 우선 검토한다.
   일반 명사는 한국어 띄어쓰기를 우선 검토하되, 게임 시스템 용어 또는
   기능명처럼 고유 명칭으로 쓰이는 말은 붙여 쓸 수 있다. `ミニドライブ`는
   공간이 충분하면 `미니|_드라이브`를 우선하고, 짧은 슬롯에서는
   `미니드라이브`처럼 붙여 써도 된다. 짧은 슬롯에서는 띄어쓰기보다 용어
   일관성과 문장 종결부 보존을 우선할 수 있다.
   예: `연료|_부족`, `|*미니드라이브|_가능합니다|.`.
5. 서식 인자에 조사가 붙으면 실제 치환 결과를 고려한다. 필요하면
   병합된 custom word 집합의 조사 관련 키를 사용하되, 기존 사용례를 먼저
   확인한다.
6. 공간에 여유가 있으면 명사형이나 지나친 축약형보다
   `~합니다|.`, `~했습니다|.`, `~하시겠습니까?` 같은 완전한 문장형을
   우선한다. `뭘로|_할까요?`, `구매할까요?`, `그만할까?` 같은 짧은
   선택형 문장은 슬롯이 부족할 때만 사용한다.
   명사형 UI 문구는 완전한 문장이 주소에 들어가지 않는 짧은 칸에만 쓴다.
   다만 주소 길이를 의미 문자로 끝까지 채우기 위해 문장이 부자연스러워지면
   자연스러운 문장을 우선하고, 남는 영역은 기존 관례의 공백·널 표기로
   채울 수 있다.
   반대로 주소가 부족할 때 숫자·영문 약어·퍼센트 기호가 포함된 문장은
   먼저 전각 표기를 반각 ASCII 표기로 바꿔 길이를 줄일 수 있는지 확인한다.
   예: `BIL`은 필요하면 `|B|I|L`, `40%`는 `|4|0|%`로 기록한다.
7. 화면 폭을 고려해 `|␂` 위치를 잡고, 각 줄의 표시 폭과 `|␂`로 나뉜
   그룹 단위의 원래 바이트 길이를 함께 고려한다. 번역문은 의미를 늘리지
   않는 범위에서 자연스럽게 배치하고, 부족분은 기존 관례의 공백·널 또는
   검증된 압축 키로 맞춘다.
8. 서로 이어 붙여 표시하는 조각 문장은 개별 항목만 직역하지 않는다.
   인접 문자열과 실행 코드의 출력 순서를 확인해, 연결했을 때 자연스러운
   한국어 어순과 조사가 되도록 각 조각을 번역한다. 조각 앞뒤에 이름,
   지명, 상품명, 수량이 붙는 경우에는 `님이시죠?`, `을|(를|)_찾고|_있나?`,
   `,돈으로|_해결하자고...`처럼 연결 결과를 기준으로 번역한다.
9. 성명 조합표, 입력 후보표, 제어용 바이트열처럼 문장이 아닌 데이터는
   번역하지 않고 원본 그대로 유지한다.

## 실행 파일의 조각 문장 확인

실행 파일에서 단독으로 불완전한 문장이 발견되면 다음 순서로 확인한다.

1. 같은 파일의 앞뒤 주소에 있는 문자열과 서식 인자를 확인한다.
2. `reverse/`의 대응 ASM에서 문자열을 사용하는 루틴과 출력 순서를
   추적한다.
3. 문자열이 실행 이미지 밖의 런타임 로드 데이터라 ASM에 직접
   라벨링되지 않은 경우, 파일 오프셋·인접 항목·제어 코드·서식 인자의
   연결 관계를 함께 근거로 사용한다.
4. 연결 문장 전체를 기준으로 높임말, 조사, 문장부호와 줄바꿈을 정한다.

## 생성 절차

1. 원본 `*_jpn.json`을 복사해 `*_kor.json`을 만든다.
2. 일반 대사 항목은 값만 번역한다. 주소 확장이 필요하면 불변 조건의
   확장 절차를 따른다.
3. 기존 `*_kor.json`을 갱신하는 작업이라면 그 파일의 `binary_input`
   같은 프로젝트별 메타데이터를 보존한다.
4. `zero_padding`, `encoding`, `custom_input`, `binary_input`은 일반 대사
   항목이 아니다. 기존 설정이나 명확한 패치 자료 없이 새로 만들거나
   번역하지 않는다.
5. 각 항목마다 주소 길이와 번역문 길이를 계산해 정확히 맞춘다.
6. 전체 파일의 주소 집합, 지원 문자, 바이트 길이를 검사한 후 바이너리
   기록을 수행한다.

## nobu5 용 추가 규칙
1. 이름에 해당하는 경우 `name_db/full_name_db.json`를 활용하여 최대한
   병합된 custom word 집합을 참고하고, 반각 조합의 이름으로 변환하여 사용한다.
   반각 조합 폰트에 공백 `_*` 또는 `*_`이 포함된 경우, 해당 반각 공백이
   주변 문자와 자연스럽게 이어지도록 번역한다.
2. 지역에 해당하는 경우도 `name_db/region_db.json`를 활용하여 최대한
   병합된 custom word 집합을 참고하여 사용한다.
3. `BFILE.NB5`처럼 `|␂`가 고정된 표시 줄 경계를 나타내는 설명문은
   전체 주소 길이뿐 아니라 `|␂`로 나뉜 각 그룹의 원래 바이트 길이를
   유지한다. 문장 의미는 줄을 넘어 이어져도 되지만, 각 줄의 바이트
   예산은 원문과 같아야 한다.
4. 위 줄 단위 설명문은 가능하면 각 줄 끝이 `|_` 같은 공백 표기로
   끝나지 않도록 문장을 조율한다. 부족분은 먼저 표현을 조정해 채우고,
   공백·널 표기는 표시와 기록에 필요한 경우에만 사용한다.
5. `BFILE.NB5` 설명문의 숫자는 가능한 한 반각 숫자 표기로 통일한다.
   예를 들어 `１５`, `１８`, `２４`는 각각 `|1|5`, `|1|8`, `|2|4`처럼
   기록한다.
6. `BFILE.NB5` 설명문은 가독성을 위해 어절 사이에 `|_`를 우선 사용한다.
   바이트를 맞추기 위해 공백을 모두 제거하지 않는다. 단, 각 줄의 바이트
   예산을 맞추기 위해 일부 어절이나 조사가 줄을 넘어갈 수 있다.
7. 실제 ASCII 공백이나 전각 공백을 직접 넣지 않는다. 공백이 필요하면
   `|_` 또는 기존 관례의 공백 표기를 사용한다. 실제 공백은 2바이트로
   계산되어 줄 예산을 깨뜨릴 수 있다.
8. `BFILE.NB5` 설명문에서도 기존 custom word 조합을 적극 활용한다. 성명
   외에도 가문명, 정권명, 통칭이 기존 조합으로 표현 가능하면 이를 우선
   검토한다. 예: `{다테}`, `{마사}{무네}`, `{하타}{케야}{마_}{요시}{츠구}`,
   `{토요}{토미}`, `{도쿠}{가와}`, `{이에}{미츠}`.
