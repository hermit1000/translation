# 일본 인명 한글 표기 규칙

이 문서는 [`name_db/full_name_db.json`](name_db/full_name_db.json)의 현재
데이터를 기준으로 일본 인명을 한글로 변환할 때 적용할 규칙을 정리한다.

## 1. 기본 원칙

한자는 이름에서 여러 독음을 가질 수 있으므로 한자 한 글자를 한글 한
음절로 기계 변환하지 않는다. 다음 우선순위를 적용한다.

1. `full_name_db.json`에서 일본어 전체 성명을 정확히 찾는다.
2. 일치 항목이 있으면 해당 항목의 `kor` 값을 그대로 사용한다.
3. 전체 성명이 없으면 기존 전체 성명에서 동일한 성과 이름 구성요소의
   표기를 각각 찾는다.
4. 구성요소 표기가 하나로 확정되지 않거나 일본어 독음을 확인할 수
   없으면 자동 등록하지 않고 검토 대상으로 남긴다.
5. 외부 사료로 일본어 독음을 확인한 뒤 아래 음역 관례를 적용한다.

즉, `武田`를 한자음인 `무전`으로 변환하는 것이 아니라 일본어 독음
`たけだ`를 확인한 뒤 `타케다`로 적는다.

## 2. DB 형식과 관찰 결과

현재 `full_name_db.json`에는 1,218개의 전체 성명이 있다.

```json
"武田 信玄": {
    "kor": "타케다 신겐",
    "game": ["nb3", "nb4", "nb5", "taiko1", "taiko2"]
}
```

형식 규칙은 다음과 같다.

- 일본어 키는 `성 + 공백 한 칸 + 이름`이다.
- `kor`도 `한글 성 + 공백 한 칸 + 한글 이름`이다.
- 현재 1,218개 `kor` 값은 모두 한글과 공백 한 칸으로만 구성되어 있다.
- 성명 앞뒤 공백, 연속 공백, 성과 이름 내부의 추가 공백을 허용하지 않는다.
- `game`은 해당 표기가 사용되는 게임 목록이며 번역 문자열의 일부가 아니다.

전체 성명에서 추출한 구성요소의 일관성은 다음과 같다.

| 구분 | 서로 다른 일본어 구성요소 | 복수 한글 표기가 있는 구성요소 |
| --- | ---: | ---: |
| 성 | 646 | 2 |
| 이름 | 1,047 | 1 |

대부분의 구성요소는 일관되지만 예외가 있으므로 전체 성명 검색을 생략하면
안 된다.

## 3. 변환 절차

### 3.1 전체 성명 exact match

입력 문자열을 임의로 정규화하기 전에 원문 그대로 검색한다.

```text
北条 氏康 → 호조 우지야스
北条 景広 → 키타조 카게히로
```

두 이름은 같은 `北条`를 사용하지만 독음이 다르다. `北条`를 항상
`호조`로 치환하면 `北条 景広`을 잘못 변환한다.

### 3.2 구성요소 기반 후보 생성

전체 성명이 없을 때만 성과 이름을 분리하여 기존 표기를 찾는다.

```text
일본어: 穴沢 信徳
성 후보: 穴沢
이름 후보: 信徳
```

두 구성요소의 한글 표기가 모두 하나로 확정될 때만 전체 성명 후보를
만든다. 다음 경우에는 사람이 확인한다.

- 구성요소가 DB에 없음
- 동일 구성요소의 한글 표기가 둘 이상임
- 관직명, 법명, 통칭 또는 별칭이 포함됨
- 게임 데이터가 실제 한자 대신 특수 코드를 사용함
- 한자 이체자 또는 게임 폰트의 오인식 가능성이 있음

### 3.3 특수 코드

코드 수와 실제 한자 수가 다르면 원시 바이트를 이름 문자열로 가장하지
않는다.

```text
0x:EC8CEC8DEC8E# 長宗我部
0x:EC8FEC8DEC8E# 香宗我部
```

`#` 뒤 설명에서 일본어 이름을 얻은 후 전체 성명 DB를 검색한다. 주소
길이는 `0x:` 뒤의 원시 바이트를 기준으로 계산하고, 한글 표기는 설명의
일본어 이름을 기준으로 결정한다.

## 4. 일본어 독음의 한글 음역 관례

아래 규칙은 일본어 독음을 이미 알고 있을 때 적용한다. 한자만 보고
독음을 결정하는 규칙이 아니다.

### 4.1 기본 음절

| 일본어 계열 | 한글 표기 원칙 | DB 예 |
| --- | --- | --- |
| か행 | 카·키·쿠·케·코 | `九鬼` → `쿠키` |
| が행 | 가·기·구·게·고 | `今川` → `이마가와` |
| さ행 | 사·시·스·세·소 | `島津` → `시마즈` |
| ざ행 | 자·지·즈·제·조 | `龍造寺` → `류조지` |
| た행 | 타·치·츠·테·토 | `武田` → `타케다` |
| だ행 | 다·지·즈·데·도 | `伊達` → `다테` |
| は행 | 하·히·후·헤·호 | `福島` → `후쿠시마` |
| ば행 | 바·비·부·베·보 | `馬場` → `바바` |
| ぱ행 | 파·피·푸·페·포 | 일본어 독음 확인 후 적용 |
| ら행 | 라·리·루·레·로 | `毛利` → `모리` |

대표적인 결합음은 다음처럼 적는다.

```text
りゅう → 류     龍造寺 → 류조지
しょう → 쇼     大友 宗麟 → 오토모 쇼린
じゅ   → 쥬     本願寺 光寿 → 혼간지 코쥬
にょ   → 뇨     本願寺 准如 → 혼간지 준뇨
```

### 4.2 촉음(っ)

촉음은 뒤 자음에 맞는 받침으로 표시하는 기존 DB 표기를 따른다.

| 일본어 이름 | 한글 표기 |
| --- | --- |
| 一色(いっしき) | 잇시키 |
| 吉川(きっかわ) | 킷카와 |
| 六角(ろっかく) | 롯카쿠 |
| 服部(はっとり) | 핫토리 |

촉음을 생략하여 `이시키`, `키카와`, `로카쿠`로 만들지 않는다.

### 4.3 발음(ん)

`ん`은 다음 음절과 기존 관용 표기를 고려해 받침으로 적는다.

```text
南部    → 난부
仙石    → 센고쿠
本願寺  → 혼간지
官兵衛  → 칸베에
```

한글 표기만 자연스럽게 만들기 위해 원문에 없는 모음을 삽입하지 않는다.

### 4.4 장음과 연속 모음

장음은 일괄적으로 `우`나 같은 모음을 추가하지 않는다. DB의 확정 표기를
우선한다.

| 일본어 이름 | DB 표기 | 주의 |
| --- | --- | --- |
| 斎藤 | 사이토 | `사이토우`로 늘리지 않음 |
| 加藤 | 카토 | `카토우`로 늘리지 않음 |
| 長宗我部 | 초소카베 | `초우소카베`로 늘리지 않음 |
| 大内 | 오우치 | `오우`가 유지되는 확정 표기 |
| 官兵衛 | 칸베에 | `에에`가 유지되는 확정 표기 |
| 慶次 | 게이지 | `에이` 계열의 확정 표기 |

따라서 장음 표기는 철자만으로 일반화하지 않고 전체 이름 또는 구성요소의
DB 표기를 재사용한다.

### 4.5 탁음과 연탁

탁음 여부는 한자 위치가 아니라 실제 일본어 독음을 따른다.

```text
武田   → 타케다
徳川   → 도쿠가와
今川   → 이마가와
新発田 → 시바타
```

같은 한자가 다른 복합어에 들어갔다고 기존 표기의 탁음 여부를 임의로
복사하지 않는다.

## 5. 한자 변형과 정규화

이체자나 신·구자체는 별도 일본어 키로 존재할 수 있다.

| 일본어 표기 | 한글 표기 |
| --- | --- |
| 斎藤 / 斉藤 | 사이토 |
| 龍造寺 / 竜造寺 | 류조지 |
| 蘆名 / 葦名 | 아시나 |

이 예들은 같은 한글 표기를 사용하지만, 모든 이체자를 자동으로 같은
글자로 바꾸라는 의미는 아니다. 원본 한자는 보존하고 DB에서 각 키를
확인한다.

가문 분파명이 한글 표기에서 생략되는 경우도 있다.

```text
上杉     → 우에스기
山内上杉 → 우에스기
深谷上杉 → 우에스기
```

이 역시 한자별 조합 규칙이 아니라 DB에 등록된 역사적 이름 단위의
정규화다.

## 6. 현재 확인된 복수 표기 예외

### 6.1 성

| 일본어 성 | 한글 표기 | 적용 전체 성명 |
| --- | --- | --- |
| 北条 | 호조 | `北条 氏康`, `北条 氏政` 등 |
| 北条 | 키타조 | `北条 景広`, `北条 高広` |
| 富田 | 토다 | `富田 景政`, `富田 長秀`, `富田 長繁` |
| 富田 | 토미타 | `富田 隆実` |

### 6.2 이름

| 일본어 이름 | 한글 표기 | 적용 전체 성명 |
| --- | --- | --- |
| 親成 | 치카나리 | `土持 親成` |
| 親成 | 치카시게 | `守屋 親成` |

이 세 구성요소는 단독 구성요소 DB만으로 자동 확정하면 안 된다.

## 7. 3코드 슬롯과 관직명 대체

NB5 인명 레코드의 성 슬롯과 이름 슬롯은 각각 최대 6바이트, 즉 2바이트
코드 3개다. 관직명을 `~노카미`, `~노스케` 형태로 한글화한 결과가 이름
슬롯의 허용 코드를 넘으면 주소를 확장하지 않는다. 관직명을 없애고 확인된
본명으로 대체한다.

```text
원본 슬롯의 성명       대체할 본명       최종 한글 출력
奥山 常陸介         → 奥山 知忠      → 오쿠야마 토모타다
木村 常陸介         → 木村 重茲      → 키무라 시게코레
橋本 豊後守         → 橋本 胤清      → 하시모토 타네키요
秋上 庵介           → 秋上 久家      → 아키아게 히사이에
笠原 美作守         → 笠原 綱信      → 카사하라 츠나노부
笠松 但馬守         → 笠松 新介      → 카사마츠 신스케
赤見 山城守         → 赤見 泰拠      → 아카미 야스요리
金上 遠江守         → 金上 盛備      → 카나가미 모리하루
鳥屋尾 石見守       → 鳥屋尾 満栄    → 토리야오 미츠히데
```

본명이 확인되지 않았거나 슬롯 제한을 넘지 않는 통칭까지 임의로 다른
이름으로 바꾸지는 않는다. 예를 들어 별도 `jpn_mod`가 없는
`山中 鹿之介 → 야마나카 시카노스케`는 DB의 확정 표기를 유지한다.

`守`를 항상 `모리`, `介`를 항상 `스케`처럼 한 글자 단위로 치환하는
것도 금지한다. 관직 독음은 원본 기록용으로 보존하되 실제 게임 출력은
슬롯에 들어가는 본명을 사용한다.

## 8. `desc` 필드 처리

현재 10개 항목에 `desc`가 있으며, 그중 9개는 위 관직명·통칭 대체와
관련된다. 이 경우 필드의 의미는 다음과 같아야 한다.

```json
"奥山 常陸介": {
    "kor": "오쿠야마 토모타다",
    "game": ["nb3", "nb4", "taiko1"],
    "desc": {
        "kor_org": "오쿠야마 히타치노스케",
        "jpn_mod": "奥山 知忠"
    }
}
```

처리 원칙:

1. JSON 키는 게임 원본 슬롯에 들어 있던 관직명·통칭 성명을 보존한다.
2. `desc.jpn_mod`는 슬롯에 대신 넣을 실제 일본어 본명이다.
3. `desc.kor_org`는 원본 관직명·통칭을 그대로 읽은 한글 표기다.
4. `kor`는 실제 출력할 본명의 한글 표기다.
5. 변환기는 `kor`를 출력하고 `kor_org`를 출력에 사용하지 않는다.
6. 구성요소 DB 검증은 원본 키와 대응하는 `kor_org`를 사용할 수 있다.

### 8.1 현재 DB의 방향이 뒤집힌 항목

현재 파일에서는 다음 7개 항목의 `kor`와 `desc.kor_org`가 위 규칙과
반대로 저장되어 있다.

| DB 키 | 현재 `kor` | 현재 `desc.kor_org` | 출력해야 할 본명 |
| --- | --- | --- | --- |
| 奥山 常陸介 | 오쿠야마 히타치노스케 | 오쿠야마 토모타다 | 오쿠야마 토모타다 |
| 木村 常陸介 | 키무라 히타치노스케 | 키무라 시게코레 | 키무라 시게코레 |
| 橋本 豊後守 | 하시모토 분고노카미 | 하시모토 타네키요 | 하시모토 타네키요 |
| 秋上 庵介 | 아키아게 이오리노스케 | 아키아게 히사이에 | 아키아게 히사이에 |
| 笠松 但馬守 | 카사마츠 타지마노카미 | 카사마츠 신스케 | 카사마츠 신스케 |
| 金上 遠江守 | 카나가미 도토미노카미 | 카나가미 모리하루 | 카나가미 모리하루 |
| 鳥屋尾 石見守 | 토리야오 이와미노카미 | 토리야오 미츠히데 | 토리야오 미츠히데 |

`笠原 美作守`와 `赤見 山城守`는 이미 `kor`에 본명,
`desc.kor_org`에 원래 관직 독음이 들어 있어 올바른 방향이다.

현재 `NameDB.validate()`의 오류 12개 중 7개는 위 필드 역전과 일치한다.
이 7개를 올바른 방향으로 바꿨다고 가정하면 검증 오류는 5개가 남는다.
남는 오류는 `一柳`, `丹後`, `日向`, `狩野` 관련 표기이므로 이 슬롯
대체 규칙과 별도로 검토한다.

- [ ] `kor`에는 출력용 본명, `kor_org`에는 원래 관직 독음을 넣었는가?
- [ ] `jpn_mod`에 대체할 일본어 본명을 기록했는가?
- [ ] 특수 코드는 `0x:HEX# 일본어 이름` 형식으로 원시 바이트를 보존했는가?
- [ ] 한글 결과가 `한글 성 + 공백 한 칸 + 한글 이름` 형식인가?
- [ ] 확정할 수 없는 구성요소를 `?` 상태로 남겨 검토했는가?

## 10. 구현 권장 순서

```text
원문 성명 파싱
  → 전체 성명 exact match
    → 있으면 kor 반환
    → 없으면 성/이름 구성요소 후보 검색
      → 두 후보가 모두 유일하면 검토 후보 생성
      → 복수 표기·미등록·특수 코드면 수동 검토
```

자동 변환 결과는 곧바로 DB에 저장하지 말고 후보 파일에서 검토한 뒤
등록한다. 기존 DB 표기와 다른 결과가 나오면 새 규칙을 적용하기보다
인물의 실제 독음과 기존 예외 여부를 먼저 확인한다.
